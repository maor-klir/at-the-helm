# Helm chart structure

A chart is a directory of files.
The Charts documentation describes it: *"A chart is organized as a collection of files inside of a directory. The directory name is the name of the chart (without versioning information)."*

Helm reads some of these files itself, at different points: when it loads the chart, when it renders the templates, during `helm install`, or during `helm test`.
Others, such as `README.md` and `LICENSE`, are there for people and for chart hubs.
Only `Chart.yaml` is required (see **02 - Benefits and limitations of Helm**).

## The layout

A chart that uses every reserved name, plus `.helmignore` and `Chart.lock`:

```text
demo/
  Chart.yaml            # required: metadata, version, dependencies
  Chart.lock            # generated by helm dependency update
  values.yaml           # default values
  values.schema.json    # optional: JSON Schema for the values
  README.md             # optional: documentation for people and hubs
  LICENSE               # optional: the chart's license
  .helmignore           # optional: paths Helm skips when it loads the chart
  charts/               # dependencies (subcharts)
  crds/                 # CustomResourceDefinitions, plain YAML
  templates/            # templates rendered with the values
    deployment.yaml
    service.yaml
    _helpers.tpl        # named templates, no output of its own
    NOTES.txt           # rendered and printed after install and upgrade
    tests/
      test-connection.yaml  # a Pod with the helm.sh/hook: test annotation
```

The Charts documentation reserves these names: *"Helm reserves use of the `charts/`, `crds/`, and `templates/` directories, and of the listed file names. Other files will be left as they are."*

Other files are packaged with the chart, and templates can read them through `.Files`, but Helm doesn't render them.
A manifest at the chart root or in a `manifests/` directory ends up in the archive and never reaches the cluster.

`helm create demo` in Helm 4.3.1 generates `Chart.yaml`, `values.yaml`, `.helmignore`, an empty `charts/`, and a `templates/` directory.
The templates are a Deployment, Service, ServiceAccount, Ingress, HTTPRoute, and HorizontalPodAutoscaler, plus `_helpers.tpl`, `NOTES.txt`, and `tests/test-connection.yaml`.

## `Chart.yaml`

`Chart.yaml` holds the chart's metadata, and Helm looks for that exact file name.
On Linux, a chart with a `chart.yaml` stops `helm template` with `unable to detect chart`.

The Charts documentation lists its fields:

| Field | Required | Purpose |
|---|---|---|
| `apiVersion` | yes | the chart API version: `v2` for charts that need Helm 3 or later |
| `name` | yes | the chart name |
| `version` | yes | the chart version, in SemVer 2 |
| `appVersion` | no | the version of the application the chart deploys; it needn't be SemVer |
| `description` | no | a single-sentence description |
| `type` | no | `application`, the default, or `library` |
| `keywords` | no | words that describe the project |
| `dependencies` | no | the other charts this chart needs |
| `kubeVersion` | no | a SemVer range of compatible Kubernetes versions |
| `home`, `sources` | no | the project's home page and source code URLs |
| `maintainers` | no | a name, email, and URL for each maintainer |
| `icon` | no | the URL of an SVG or PNG icon |
| `deprecated` | no | whether the chart is deprecated |
| `annotations` | no | custom metadata, keyed by name |

**A missing required field stops rendering, installing, and packaging:** without `name`, `helm template`, `helm install`, and `helm package` fail with `validation: chart.metadata.name is required`.

### `apiVersion`

The Charts documentation defines the two values: *"The `apiVersion` field should be `v2` for Helm charts that require at least Helm 3. Charts supporting previous Helm versions have an `apiVersion` set to `v1` and are still installable by Helm 3."*
`v2` added the `dependencies` field, which `v1` charts kept in a separate `requirements.yaml`, and the `type` field.

`helm lint` in Helm 4.3.1 accepts only these two: `apiVersion 'v3' is not valid. The value must be either "v1" or "v2"`.
Charts v3 is still experimental (see **02 - Benefits and limitations of Helm**).

### `name`

Helm takes the chart's name from `Chart.yaml`, not from the directory.
A chart in a directory called `other/` with `name: demo` lints without an error, and `helm package` saves it as `demo-0.1.0.tgz`.

### `version` and `appVersion`

The two fields are independent: `version` changes with every change to the chart, and `appVersion` with the application it deploys (see **01 - The role of Helm in Kubernetes**).
The Charts documentation asks for SemVer 2 in `version`: *"Every chart must have a version number. A version should follow the SemVer 2 standard but it is not strictly enforced."*

A version that isn't SemVer at all is rejected: `version: foo` stops `helm template`, `helm install`, and `helm package` with `validation: chart.metadata.version "foo" is invalid`.
`helm lint` only warns about a version such as `v1.2.3`, which `helm package` still accepts: `version 'v1.2.3' is not a valid SemVerV2`.

`appVersion` has no format rules, and the documentation recommends quoting it: *"Wrapping the version in quotes is highly recommended. It forces the YAML parser to treat the version number as a string."*
Unquoted, `1.0` is read as a floating-point number.

### `description`, `keywords`, and `type`

**`helm search repo` matches `keywords` as well as the name and description:** `helm search repo cms` lists `bitnami/wordpress`.
Its name and description don't contain "cms", but its keywords do: `application`, `blog`, `cms`, `http`, `php`, `web`, and `wordpress`.

`type: library` makes a chart that other charts include and that can't be installed on its own (see **21 - Why create our own charts**).

### `dependencies`

Each entry names another chart, a version or range, and the repository to fetch it from (see **21 - Why create our own charts**).
A dependency is rendered with the parent chart and installed in the same release.
Our WordPress release includes the MariaDB StatefulSet from its `mariadb` dependency, and `helm get metadata` lists `DEPENDENCIES: common,mariadb`.

### Fields outside the list

The Charts documentation says *"additional fields are not allowed. The recommended approach is to add custom metadata in `annotations`."*
Helm 4.3.1 is less strict: a `foo: bar` line in `Chart.yaml` makes `helm lint` warn `failed to strictly parse chart metadata file`, and the chart still renders and packages.

## `Chart.lock`

`helm dependency update` writes `Chart.lock` with the exact version it resolved for each dependency.
`helm dependency build` rebuilds `charts/` from that file without resolving the ranges again (see **02 - Benefits and limitations of Helm**).

## `values.yaml` and `values.schema.json`

The Charts documentation names the two sources of values: *"Chart developers may supply a file called `values.yaml` inside of a chart. This file can contain default values."*
Chart users supply their own values with `--values` and `--set`, which override those defaults (see **13 - Overriding chart values**).

**A setting that comes from `values.yaml` can be changed per installation:** a literal written into a template can't, short of changing the chart (see **03 - Helm vs. Kustomize**).
The best practices ask for every value to be documented in `values.yaml` (see **02 - Benefits and limitations of Helm**).

`values.schema.json` is an optional JSON Schema for the values; `helm install`, `helm upgrade`, `helm lint`, and `helm template` stop when the values don't match it (see **02 - Benefits and limitations of Helm**).

## `README.md` and `LICENSE`

`README.md` documents the chart: what it deploys, its prerequisites, its values with their defaults, and anything else needed to install or configure it.
Chart hubs display it, and `helm show readme` prints it without installing the chart (see **02 - Benefits and limitations of Helm**).

`LICENSE` is a plain text file with the chart's license.
The Charts documentation explains why a chart has one of its own: *"The chart can contain a license as it may have programming logic in the templates and would therefore not be configuration only. There can also be separate license(s) for the application installed by the chart, if required."*

## `.helmignore`

`.helmignore` lists paths Helm leaves out of the chart.
Its documentation covers more than packaging:

> *"If this file exists, Helm ignores every path that matches a pattern when it loads the chart. That applies to `helm package`, and also to commands that render or install the chart directly from a directory, such as `helm install`, `helm upgrade`, and `helm template`."*

With `draft-*` added to the scaffold's `.helmignore`, a `templates/draft-configmap.yaml` is missing from both `helm template` output and the packaged archive.

Patterns are globs matched with Go's `filepath.Match`, one per line, with `!` for negation.
Unlike `.gitignore`, `**` isn't supported, and the file *"does not exclude itself by default"*.
The scaffold's `.helmignore` lists version control directories, editor files, and backup files, but not itself, so `.helmignore` ends up in the archive.

## `charts/`

`charts/` holds the chart's dependencies, also called subcharts, in one of two forms.
`helm dependency update` downloads the entries in `Chart.yaml` and stores them as archives such as `postgresql-16.2.5.tgz`.

A dependency can also be copied in by hand: *"A dependency should be an unpacked chart directory but its name cannot start with `_` or `.`. Such files are ignored by the chart loader."*
Helm refuses to render or install a chart whose listed dependencies are missing from `charts/` (see **01 - The role of Helm in Kubernetes**).

**A plain manifest in `charts/` stops the chart from loading:** Helm loads every entry there as a subchart, except names that start with `_` or `.`.
A `charts/database.yaml` stops `helm template`, `helm lint`, and `helm package` with `error unpacking subchart database.yaml in nginx: Chart.yaml file is missing`.

## `crds/`

`crds/` holds CustomResourceDefinitions: *"CRD files _cannot be templated_. They must be plain YAML documents."*
`helm install` creates them first and waits until the API server serves them, so the templates can create objects of the new kinds.

The Charts documentation limits what happens to them afterwards:

> *"CRDs are never installed on upgrade or rollback. Helm will only create CRDs on installation operations."*

Helm also never deletes them, and `helm template` leaves them out unless `--include-crds` is given (see **02 - Benefits and limitations of Helm**).

## `templates/`

The Charts documentation describes the directory: *"All template files are stored in a chart's `templates/` folder. When Helm renders the charts, it will pass every file in that directory through the template engine."*
Most files render to Kubernetes manifests, which Helm sends to the API server.
`NOTES.txt` and files whose names start with an underscore are the exceptions.

**A template doesn't need any template actions:** text outside `{{ }}` is copied to the output unchanged (see **01 - The role of Helm in Kubernetes** and **23 - Template syntax basics**).
A plain Deployment manifest in `templates/` is therefore a valid template, and Helm installs it as written.

The best practices set the naming:

- *"Template files should have the extension `.yaml` if they produce YAML output. The extension `.tpl` may be used for template files that produce no formatted content."*
- *"Template file names should use dashed notation (`my-example-configmap.yaml`), not camelcase."*
- *"Each resource definition should be in its own template file."*

### `_helpers.tpl` and other underscore files

The chart template guide describes files whose names start with an underscore: *"These files are not rendered to Kubernetes object definitions, but are available everywhere within other chart templates for use."*
They hold named templates, created with `define` and used with `include`.

**Helm discards any output of an underscore file:** a `templates/_extra.tpl` that holds a ConfigMap next to a `define` adds no ConfigMap to the rendered manifests.
Its named template is still available to every other template.

**The underscore doesn't make a named template global:** a `define` in a plain `templates/defs.yaml` can be included from any template too.
Named templates are shared by a chart and all of its subcharts, so the best practices ask for names prefixed with the chart name, as `helm create` does with `demo.fullname` and `demo.labels`.

### `NOTES.txt`

The Charts documentation describes the file: *"This file is evaluated as a template, and can be used to display usage notes, next steps, or any other information relevant to a release of the chart."*
Helm prints it after `helm install` and `helm upgrade`, and `helm status` and `helm get notes` print it again (see **11 - Exploring charts and releases with the Helm CLI**).

It isn't a manifest, so `helm template` leaves it out of its output.
A subchart's `NOTES.txt` is printed only with `--render-subchart-notes`: *"if set, render subchart notes along with the parent"*.
The documentation also asks to *"keep the content brief and point to the README for greater detail."*

### `tests/`

What makes a template a test is its annotation, not its directory.
The chart tests documentation defines a test:

> *"A **test** in a helm chart lives under the `templates/` directory and is a workload definition (commonly a Pod or Job) that specifies a container with a given command to run. The container should exit successfully (exit 0) for a test to be considered a success. The definition must contain the helm test hook annotation: `helm.sh/hook: test`."*

`templates/tests/` is a convention: *"You are welcome to nest your test suite under a `tests/` directory like `<chart-name>/templates/tests/` for more isolation."*
A test is a hook, so `helm install` doesn't create it; the `test` hook *"Executes when the Helm test subcommand is invoked"*.

The scaffold's `tests/test-connection.yaml` is a busybox Pod that runs `wget` against the chart's Service.
`helm test <release>` creates it and reports whether it exited with 0.

## When Helm reads each part

| Path | Read by | When |
|---|---|---|
| `Chart.yaml` | Helm | every command that loads the chart |
| `Chart.lock` | `helm dependency build` | rebuilding `charts/` at the locked versions |
| `values.yaml`, `values.schema.json` | Helm | rendering and validation in `template`, `install`, `upgrade`, and `lint` |
| `README.md` | people and chart hubs | `helm show readme`, Artifact Hub |
| `LICENSE` | people | when reusing or redistributing the chart |
| `.helmignore` | Helm | loading the chart from a directory, including `helm package` |
| `charts/` | Helm | rendered and installed with the parent chart |
| `crds/` | Helm | `helm install` only, before the templates |
| `templates/*.yaml` | Helm | rendering; the output goes to the API server |
| `templates/_*.tpl` | Helm | rendering; named templates only, no output |
| `templates/NOTES.txt` | Helm | printed after `install` and `upgrade`, and by `status` |
| `templates/tests/` | Helm | created by `helm test` |

## Verify

In an empty directory, the scaffold shows the layout:

```bash
cd "$(mktemp -d)"
helm create demo
find demo | sort
```

It has `Chart.yaml`, `values.yaml`, `.helmignore`, an empty `charts/`, and `templates/` with `_helpers.tpl`, `NOTES.txt`, and `tests/`, but no `values.schema.json`, `README.md`, `LICENSE`, `Chart.lock`, or `crds/`.

The archive shows what `.helmignore` leaves out:

```bash
touch demo/notes.bak
helm package demo
tar tzf demo-0.1.0.tgz
```

The scaffold's `.helmignore` lists `*.bak`, so `notes.bak` is missing from the archive, while `.helmignore` itself is in it.
The empty `charts/` directory is left out as well, because the archive holds only files.
